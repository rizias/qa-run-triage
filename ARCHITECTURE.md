# Архитектура qa-run-triage

## Части системы

- `src/access.ts` — решает, разрешена ли джоба полем настроек `allowedJobs`, и отказывает единообразно во всех поверхностях.
- `src/config.ts` — читает три файла и три схемы: общий файл `config.json` в корне `~/.qa-run-triage` (`profile`, `bindings`), файл профиля `profile.json` (`description`, `servers`, `defaultServer`, `repos`, `environment`, `jobs`, `allowedJobs`, `limits`, `report`) и файл секретов `credentials.json` («имя сервера → поля режима»: `proxyUser`, `proxyPass` для `basic`, `user`, `token` для `token`, без обязательной записи для `none`). Переменные окружения есть у полей серверов (`QA_RUN_TRIAGE_SERVER_<ИМЯ>_<ПОЛЕ>`), пределов, `report.timeZone`, каталога данных и профиля; у остальных полей, в том числе `description`, переменной нет. Профиль выбирается в таком порядке: `--config <путь>` (каталог файла — каталог профиля), `--profile <имя>`, переменная `QA_RUN_TRIAGE_PROFILE`, привязка папки из `bindings` общего файла (самое длинное совпадение пути; на Windows ключ — буква диска или UNC), поле `profile` общего файла, `default`. Каждый файл проверяется по строгой схеме, значения отдаются с источником.
- `src/settings.ts` — часовой пояс отчёта `report.timeZone` и числовые пределы работы и формата отчёта, включая несжатый размер одного архива `archiveMaxBytes` (2147483648); значения берутся из общего чтения настроек: переменная, файл, умолчание.
- `src/commonConfig.ts` — читает общий файл `config.json`, проверяет имя профиля и выбирает профиль по порядку источников: `--config`, `--profile`, переменная, привязка папки, поле `profile`, `default`.
- `src/configFields.ts` — схема полей настроек: список `CONFIG_FIELDS` с именами, переменными окружения и значениями по умолчанию, пути файлов профиля и общего файла, умолчания для `config init`, включая `auth: "basic"` и пояс машины.
- `src/configDescribe.ts` — собирает ответ команды `config` / `config --json`: значение и источник (`env`, `file`, `default`) каждого поля, серверов, `jobs` и `environment`; секреты только отметкой «задан» или «не задан».
- `src/configValidation.ts` — проверяет файлы настроек по строгой схеме: неизвестное поле, значение неверного типа, число вне диапазона. `src/serverAuth.ts` проверяет режим и поля секретов с учётом окружения: в `none` запись игнорируется; в `basic` и `token` чужие поля отклоняются без вывода значений.
- `src/lock.ts` — файловый замок с PID, временем старта и токеном владельца; сериализует перехват замка мёртвого процесса и проверяет токен перед освобождением, используется журналом и общим файлом.
- `src/serverResolution.ts` — разрешает поля сервера (`kind`, `auth`, `baseUrl`, `reportArtifact`, `workspaceNodeMax`, секреты выбранного режима) по переменной, файлу и умолчанию, каждое со своим источником.
- `src/cli` — `args.ts` разбирает аргументы и глобальные флаги `--config` и `--profile`, отвергает отсутствующий или нецелый номер билда, нецелые дни `query` и `limit` у `runs`, `limit` выше `runListMax` и лишние токены; `failures` без джобы называет джобу; `src/cli/config/` печатает настройки и создаёт файл по `config init` (без `--config`); обработчики команд живут в `src/cli/commands.ts`; `index.ts` — точка входа, для `config init`/`profiles`/`use` не читает текущий профиль и печатает цепочку причин строками `Причина: `.
- `src/digest` — строит сводку прогона и список упавших или восстановившихся после перезапуска тестов.
- `src/fetcher` — скачивает прогон, безопасно распаковывает архивы (пропуск zip-slip и симлинков, предел несжатого размера), размещает их в кэше и удаляет старые прогоны. `checkouts.ts` извлекает из консольного лога все checkout джобы: имя репозитория и коммит; односегментное имя сопоставляет с клоном только при уникальном последнем сегменте среди `repos`.
- `src/htmlreport` — собирает из журнала поколения статического HTML-отчёта; окно главной страницы и часовой пояс берутся из уже загруженных `settings` выбранного профиля. Пояс используется при группировке по месяцам и сохраняется в данных поколения для форматирования дат в браузере; смещение UTC вычисляется на дату сборки.
- `src/ci` — нейтральный клиент сервера прогонов (`CiClient`) и фабрика `createCiClient`: вид выбирается по `servers.<имя>.kind`, сейчас только `jenkins`. Команды зависят от интерфейса, не от адаптера.
- `src/jenkins` — реализация kind `jenkins`: пути и запросы Jenkins, HTTP-чтение и ответы. Клиент создаётся фабрикой по имени сервера в момент, когда команда знает джобу: сервер берётся из свойства `server` совпавшей записи `jobs` (`src/jobs.ts`), иначе из `defaultServer` профиля; команда показа джоб и папок — тем же правилом, включая единственный сервер без `defaultServer`. Для kind `jenkins` поле `servers.<имя>.workspaceNodeMax` задаёт, до какого номера узла ищется рабочий каталог.
- `src/journal` — читает, дополняет и чинит журнал разборов `journal.jsonl`. Замок пишет PID и время старта держателя и перехватывает сорванный замок мёртвого процесса. Дозапись отсутствующих записей пишет через временный файл и переименование. `repair` разрешает сервер как остальные команды и подтверждает пустой отчёт сводкой Allure. Метаданные билда при дозаписи дают «нет» только на 404.
- `src/report` — читает JSON Allure, выделяет основные записи тестов и вложения.
- `src/sources` — кэширует архивы исходников и находит файл теста по имени класса Java или по пути относительно корня репозитория; идентификатор с абсолютным путём, диском, обратным слэшем, управляющим символом или сегментом `.` / `..` отвергается до чтения, хвост `:строка:столбец` снимается и у имени класса, а итоговый путь архива проверяется на выход за корень. Когда архива в кэше нет, читает файл из локального клона по коммиту прогона. Клоны-кандидаты — записи `repos` профиля, чьё происхождение (`origin`) совпадает по идентичности репозитория (`src/fetcher/checkouts.ts`: два последних сегмента пути адреса без `.git`, без учёта регистра) хотя бы с одним checkout'ом прогона; односегментное сохранённое имя совпадает, только если последний сегмент уникален среди `repos`; битая запись `repos` не обрывает остальные клоны; коммит берётся из checkout'а, с которым совпал клон.
- `src/skills` — ставит скилл пакета агентам по выбору пользователя, хранит реестр установок в `~/.qa-run-triage/skills-registry.json`, обновляет копии при смене версии пакета и сообщает о новой версии в npm.

## Потоки данных

1. `fetch` запрашивает у сервера CI метаданные билда и консольный лог, затем скачивает артефакт отчёта Allure (имя задаёт `servers.<имя>.reportArtifact`, по умолчанию `allure-report.zip`), если он есть. Архив фильтруется до `data/test-cases/`, `data/attachments/`, `widgets/` и `history/` и публикуется вместе с `meta.json` и `manifest.json` в `CACHE_DIR/runs/КЛЮЧ_ДЖОБЫ/НОМЕР_БИЛДА`.
2. `readTestCases` читает `report/allure-report/data/test-cases/*.json`, а `readAllureSummary` — `report/allure-report/widgets/summary.json`. Записи с `retry: true` и `hidden: true` исключаются из основных и сверяются с `statistic.total`.
3. `buildSummary` объединяет основные записи Allure с метаданными билда; `listFailures` выдаёт падения или тесты, прошедшие после перезапуска, вместе с точным текстом ошибки, историей, параметрами и вложениями.
4. `journal-append` принимает результат разбора, заново получает отпечатки падений из кэшированного Allure и дополняет запись метаданными билда. `record-runs` отдельно добавляет отсутствующие успешные прогоны. Записи сохраняются по тройке server, job и build в `CACHE_DIR/journal.jsonl`. Прежняя строка без server относится к текущему серверу джобы; дозаполнение записывает его.
5. `report` читает `journal.jsonl`, группирует записи и отпечатки по времени, серверу, джобе и окружению и пишет поколение в `journal-report/gens/`; `journal-report/current.js` переключается на него, а `journal-report/index.html` служит входной страницей. Ссылки различают одинаковые джобы разных серверов.
6. При скачивании состав прогона — пары «полное имя теста, исход» — записывается в `CACHE_DIR/test-sets/SHA256.json`; `journal-append` и `repair` кладут в запись журнала ссылки `testSetHash` и `sourceHash`. Очистка кэша эти файлы не трогает.

Исходники идут отдельным путём: `fetchRun` берёт `src.zip` из артефактов билда, а при его отсутствии для kind `jenkins` пробует ZIP рабочего каталога Jenkins и отмечает свежесть по коммитам. `cacheSources` считает SHA-256, распаковывает только `src/` и хранит одну копию в `CACHE_DIR/sources-by-hash/SHA256`; `manifest.json` прогона содержит ссылку на этот хэш. `source` преобразует имя Java-класса в пути `src/main/java` и `src/test/java` и читает единственный найденный файл; ответ из архива несёт `freshness`, ответ из репозитория — `repository` и `commit`.

## Внешние системы

- **Сервер CI (kind `jenkins`: Jenkins HTTP API)** — вызываются только GET-запросы к `api/json`, `consoleText`, артефактам билда и ZIP рабочего каталога. Они нужны для списка джоб и прогонов, метаданных, лога, Allure и исходников; доступ к этим ресурсам определяется сервером. В `none` заголовок `Authorization` отсутствует, в `basic` передаётся HTTP Basic с парой `proxyUser:proxyPass`, в `token` — с парой `user:token`. Права записи на сервере CI не используются.
- **Локальная файловая система** — процессу нужны права чтения и записи в `CACHE_DIR`, а для `report --out-dir` — в выбранный каталог. Кэш, журнал и HTML состоят из каталогов, JSON/JSONL, ZIP и статических файлов; базы данных нет.
- **Локальные клоны репозиториев автотестов** (список `repos` в настройках) — только чтение файла по коммиту прогона командой git; сеть не используется, отсутствие коммита в клоне — ошибка с причиной.
- **Реестр npm** — не чаще раза в сутки фоновый процесс спрашивает последнюю версию пакета; команда `update` ставит её через npm.
- **Стандартный ввод и вывод** — разбор подаётся команде записи объектом JSON, результат печатается в стандартный вывод.

## Точки входа

Всё входит через `src/cli/index.ts`: он разбирает аргументы, проверяет границу доступа и вызывает обработчик из `src/cli/commands.ts`. Список команд — в README.md, список npm-скриптов — в package.json.

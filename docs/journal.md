# Журнал разборов

Журнал — файл `<cacheDir>/journal.jsonl`: одна JSON-запись на сочетание сервера, джобы и номера билда.
Прежняя строка без `server` принадлежит текущему серверу джобы; дозаполнение записывает его.
Поиск показывает сервер в идентификаторе прогона. Изменение идентичности само по себе не переписывает журнал.
В записи хранятся результат и окружение прогона, числа тестов, точные тексты ошибок, вердикт
агента, метаданные билда и разбора, а также две ссылки на данные прогона: `testSetHash` —
сумма состава выполненных тестов, `sourceHash` — сумма архива исходников. Сами составы лежат
в `<cacheDir>/test-sets/<сумма>.json` — массив пар «полное имя теста, исход» — и не удаляются
никакой очисткой: по ним видно, какие тесты выполнялись в прогоне, даже когда билда давно нет.

В начале разбора выполняется `record-runs`: инструмент добавляет ещё не записанные зелёные
прогоны и сообщает о прогонах, которые нужно разобрать. После анализа вердикт записывается
командой `journal-append`, она же пересобирает HTML-отчёт.

Запись без значения окружения считается неполной. При следующем `record-runs` инструмент
пытается дозаполнить окружение из параметров билда.

## Вход `journal-append`

Объект JSON на стандартном вводе проверяется схемой `analysisSchema` в
`src/journal/appendAnalysis.ts`. Схема строгая: неизвестное поле — ошибка использования, ещё до
записи в журнал. Поле `build`, переданное строкой, а не числом, — тоже ошибка: тип не совпадает
со схемой. Вход длиннее `limits.journalInputMaxBytes` (по умолчанию 1048576 байт) обрывает
чтение стандартного ввода раньше разбора JSON — запись в журнал не выполняется.

| Поле | Тип | Обязательно | Если не передано |
|---|---|---|---|
| `job` | строка | да | — |
| `build` | целое положительное число | да | — |
| `testsRan` | булево | да | — |
| `recoveredAfterRetry` | целое неотрицательное число | да | — |
| `verdict` | строка | да | — |
| `env` | строка | нет | `''`, инструмент пытается дозаполнить из параметров билда |
| `city` | строка | нет | `''`, инструмент пытается дозаполнить из параметров билда |
| `branch` | строка | нет | `''` |
| `codeBranch` | строка | нет | `''` |
| `result` | строка или `null` | нет | `null` |
| `total` | целое неотрицательное число или `null` | нет | `null` |
| `failed` | целое неотрицательное число или `null` | нет | `null` |
| `fingerprints` | массив строк | нет | `[]`, при `testsRan: true` и скачанном отчёте инструмент пересчитывает их сам из отчёта |
| `model` | строка | нет | `''` |
| `analysisDurationMs` | целое неотрицательное число | нет | `0` |
| `tokensIn` | целое неотрицательное число | нет | `0` |
| `tokensOut` | целое неотрицательное число | нет | `0` |
| `buildTimestamp` | число или `null` | нет | берётся из кэшированного `meta.json` прогона, если поле не передано вовсе |
| `durationMs` | число или `null` | нет | берётся из кэшированного `meta.json` прогона, если поле не передано вовсе |
| `commit` | строка или `null` | нет | берётся из кэшированного `meta.json` прогона, если поле не передано вовсе |
| `buildUrl` | строка или `null` | нет | строится из адреса сервера, если поле не передано вовсе |

Кроме проверки схемы, инструмент сам заполняет и не даёт переопределить: `testSetHash` и
`sourceHash` (ссылки на состав прогона и архив исходников), `server` (сервер, к которому
относится джоба) и `analyzedAt` (момент записи). Значение `testsRan`, если оно `true`, а отчёт
скачан, пересчитывается инструментом по отчёту вместе с `fingerprints`; переданное значение
`testsRan: false` инструмент не трогает.

Поле `env`: пустая строка или отсутствие поля не отклоняются — схема принимает `''` по
умолчанию. Если после попытки инструмента дозаполнить его из параметров билда `env` всё равно
остаётся пустым, запись сохраняется как есть; построение HTML-отчёта (`src/htmlreport/reportData.ts`)
в этом случае просто отмечает запись как неполную (`incomplete: true`) и учитывает её в счётчике
неполных записей на главной странице отчёта — ни ошибки, ни отказа в записи из-за пустого `env`
не происходит.

Пример 1 — прогон, в котором тесты выполнялись:

```json
{
  "job": "folder/example-job",
  "build": 42,
  "env": "stage",
  "city": "example-city",
  "branch": "release/2026.09",
  "codeBranch": "main",
  "result": "FAILURE",
  "testsRan": true,
  "total": 120,
  "failed": 3,
  "recoveredAfterRetry": 1,
  "verdict": "Падения из-за таймаута прокси на стенде, не дефект продукта.",
  "fingerprints": ["Timeout of 30000ms exceeded waiting for selector"],
  "model": "example-model",
  "analysisDurationMs": 42000,
  "tokensIn": 15000,
  "tokensOut": 800
}
```

Пример 2 — прогон, упавший до запуска тестов (тестовых результатов ещё нет):

```json
{
  "job": "folder/example-job",
  "build": 43,
  "env": "stage",
  "city": "example-city",
  "branch": "release/2026.09",
  "testsRan": false,
  "recoveredAfterRetry": 0,
  "verdict": "Сборка упала на этапе checkout: недоступен git-репозиторий."
}
```

## Замок журнала и параллельная запись

Запись в журнал (`journal-append`, `record-runs`, `repair`) идёт под файловым замком
`<cacheDir>/journal.jsonl.lock` (`withFileLock` в `src/lock.ts`, вызывается через
`withJournalLock` в `src/journal/journal.ts`). Замок — файл, создаваемый эксклюзивно (`wx`); пока
он существует, второй процесс не может писать и раз в `limits.journalLockPollMs` (по умолчанию
20 мс) пробует снова, пока не пройдёт `limits.journalLockTimeoutMs` (по умолчанию 5000 мс).

Если время ожидания истекло, процесс завершается ошибкой:

```
Файл занят другим процессом: замок <cacheDir>/journal.jsonl.lock не освободился за 5000 мс.
```

Два процесса, пишущие в журнал одновременно, не теряют данные и не портят файл: первый
получает замок, читает весь `journal.jsonl`, добавляет или заменяет свою строку и записывает
файл атомарно (запись во временный файл и `rename`, `atomicWriteFile` в `src/lock.ts`), затем
снимает замок. Второй всё это время ждёт (опрашивая с шагом `journalLockPollMs`) и, получив
замок уже после первого, читает журнал заново — то есть видит запись первого процесса и не
перетирает её. Если ожидание второго процесса упирается в `journalLockTimeoutMs`, его команда
просто завершается ошибкой выше (код возврата 1) без записи — журнал остаётся в состоянии
первого писавшего процесса, порчи данных нет, только неудача самой команды.

Если процесс, державший замок, аварийно завершился, не сняв замок, следующий писатель не ждёт
таймаут: `reclaimIfStale` в `src/lock.ts` проверяет PID, записанный в файле замка
(`process.kill(pid, 0)`), и если процесс с этим PID не существует, сам снимает старый замок и
печатает в стандартный поток ошибок:

```
Замок <lockFile> снят: процесс <pid> не существует.
```
# Сохранность при дозаполнении и починке

`record-runs` получает параметры по сети вне замка и под замком перечитывает строку.
Дозаполняются только пустые `env`, `city`, `server`, `buildUrl`; новый разбор сохраняется.
`repair` сохраняет непонятные строки на месте, включая JSON с неподходящей схемой,
и сообщает о них. Перед изменением создаётся новая `journal.jsonl.bak-<UTC timestamp>`.

Все присутствующие поля проверяются по типам до заполнения умолчаний. Неверный тип
сохраняет исходную строку буквально, вместе с дополнительными полями. Починка не использует
кэш другого сервера или адреса; ошибка состава одной записи сохраняет её и не мешает остальным.
Перехват старого замка сериализован отдельным захватом с повторной проверкой владельца.
Освобождение удаляет только файл с собственным токеном; незавершённый захват мёртвого
процесса также может быть восстановлен.

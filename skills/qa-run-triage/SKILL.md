# Разбор прогона автотестов

Инструмент не настроен или команда отвечает ошибкой настроек — настройка с нуля описана в
README пакета, раздел «Настройка»; путь README: рядом с этим пакетом,
`npm root -g`/@rizias/qa-run-triage/README.md. Подробные документы пакета лежат там же, в папке `docs/`: `settings.md`, `journal.md`, `storage.md`, `report.md`, `allure.md`, `glossary.md`.
Поддерживается только сервер CI вида `jenkins`. Прогоны из GitHub Actions, GitLab CI и других
систем инструмент не читает — так и сказать пользователю.

## Порядок

Узнать имена джоб и папок — `qa-run-triage jobs`; список прогонов джобы — `qa-run-triage runs`.

Джоба не названа пользователем (например, «разбери ночной прогон») — сначала
`qa-run-triage jobs [папка]`, показать список папок и джоб и спросить владельца, какая джоба
нужна, одним вопросом. После ответа — `qa-run-triage runs <джоба>`: в списке у каждого билда
поля `timestamp` (миллисекунды от начала эпохи) и `result`; билд под «вчера ночью» ищется по
`timestamp`.

0. `qa-run-triage config --json` — показывает текущий профиль и чем он выбран, серверы и группы джоб, поле `notesFile`: если файл есть, прочитать его до разбора. В нём владелец держит знания об инфраструктуре, которых нет в отчётах: смысл параметров билда, срок жизни билдов в CI, особенности джоб. Узнал такой факт по ходу разбора — предложить владельцу дописать его туда; без слова владельца файл не менять. Файл `credentials.json` агент не открывает и секреты не печатает — команда `config --json` их никогда не выдаёт.
1. `qa-run-triage record-runs <джоба>` — зелёные запишутся сами, в ответе список прогонов на разбор; уже разобранные прогоны (есть запись в журнале с вердиктом) в список не попадают, их число — в поле «разобрано ранее».
2. `qa-run-triage fetch <джоба> <билд>` — скачать прогон в кэш. Нужен для `summary`, `failures` и `source` из архива; остальные команды без скачивания работают.
3. `qa-run-triage summary <джоба> <билд>` — `testsRan: false` значит сбой до тестов (сборка, таймаут, доступы): разбирать `console.log` прогона, а не тесты. `reportEmpty: true` — частный случай того же: отчёт скачан, но в нём нет ни одной записи, раннер упал до первого теста; причину тоже искать в `console.log`. Поле `parameters` печатается целиком, включая значения параметров билда.
4. `qa-run-triage failures <джоба> <билд>` — падения: точный текст ошибки, `testClass`, `testMethod`, `retriesCount`, `historyStatuses`, скриншоты. С `--recovered` — прошедшие после повтора. Без джобы, в том числе `failures --recovered`, команда завершается ошибкой использования, называющей джобу. Без целого номера билда, в том числе `failures <джоба> --recovered`, команда завершается ошибкой использования, называющей билд.
5. Сгруппировать падения по тексту ошибки, не по тестам: один текст на двадцать тестов — одна причина.
6. `qa-run-triage query "<текст ошибки>" [дней]` — встречалась ли причина раньше и где. Без аргумента дней окно поиска равно `limits.fingerprintLookbackDays` (по умолчанию 30). Нецелое или неположительное число дней — ошибка использования.
7. `qa-run-triage source <джоба> <билд> <идентификатор>` — код теста из этого билда. Идентификатор: для Java `testClass` из падения, для Playwright `testFile`; хвост `:строка:столбец` снимается и у пути, и у имени класса. Абсолютный путь, буква диска, обратный слэш, управляющий символ и сегменты `.` / `..` — ошибка, файл вне исходников прогона не читать. `freshness.isCurrent: false` — код архива новее прогона. Если архива в кэше уже нет, файл читается из клона в `repos`, чьё происхождение совпадает с checkout'ом прогона; ответ называет репозиторий и коммит; `origin: repository` в ответе — код закоммиченный, без файлов, созданных при сборке. Битая запись `repos` не обрывает остальные клоны и входит в итоговую ошибку. Если ни один клон не подошёл, ошибка называет для каждого checkout'а прогона причину: клон не найден в `repos`, имя неоднозначно (односегментное имя и несколько клонов с тем же последним сегментом), либо клон найден, но не читается — с конкретной причиной (нет коммита, нет файла в коммите, путь не git-репозиторий).
8. `qa-run-triage journal-append < разбор.json` — записать вердикт; отчёт пересоберётся тем же вызовом.

Большие выводы обрабатывать скриптом и печатать итог, целиком в контекст не тащить.

## Подпись причины — точный текст ошибки

- Не чистить, не сокращать, не заменять числа, пути и идентификаторы.
- Разные тексты — разные причины, пока обратное не доказано в вердикте с уликами.
- Успех после повторов сам по себе не определяет причину: проверяй среду, тайминги и перемежающийся дефект продукта по ошибкам и шагам теста.

## Ушла ли проблема — решает агент, не инструмент

Текст мог исчезнуть по четырём причинам: починили; тест переписали; тест отключили; тест не входил в набор этого прогона. На одном коде могут запускаться разные наборы; частоту причин нужно устанавливать по данным прогонов. Проверка:

- Запускался ли тест: состав прогона — массив пар «полное имя, исход» — лежит в `<кэш>/test-sets/<testSetHash>.json`; `testSetHash` есть в записи журнала. Для скачанного прогона то же самое — файлы `report/allure-report/data/test-cases/*.json`, поле `fullName`. Нет теста в составе — прогон об этой проблеме не говорит ничего.
- Менялся ли тест: `source` по двум билдам, сравнить.
- Менялся ли код продукта: поле `commit` в записях журнала.
- Путь к кэшу показывает `qa-run-triage config --json`, поле `cacheDir`; каталог джобы в `runs/` искать по началу имени.

Срок хранения билда в CI задаётся сервером; если он известен, его можно найти в заметках владельца; скачанный прогон — до вытеснения из кэша; журнал, составы и отчёт не удаляются никогда. Всё, что понадобится потом, записывать в вердикт сейчас — с уликами: что проверено, где, почему такой вывод.

На диске (кратко, подробности и пути — в docs/storage.md пакета): скачанные прогоны `runs/` держатся числом `limits.cacheKeepRuns` на джобу и старше предела удаляются очередным `fetch`; исходники `sources-by-hash/`, составы `test-sets/`, журнал `journal.jsonl` и все поколения HTML-отчёта `journal-report/gens/` не удаляются никогда.

## Запись разбора

Обязательные поля: `job`, `build`, `testsRan`, `recoveredAfterRetry`, `verdict`. Окружение `env` заполнять всегда: без него запись неполная. `fingerprints` можно не передавать — возьмутся из отчёта. `reportError` в ответе — отчёт не собрался, запись цела, ошибку назвать пользователю.

Пример минимального объекта: `{"job":"folder/example-job","build":42,"env":"stage","testsRan":false,"recoveredAfterRetry":0,"verdict":"…"}`. Полная схема поля, что заполняется автоматически и что отклоняется — в docs/journal.md пакета.

`repair` чинит только журнал и не пересобирает HTML-отчёт — после него для отчёта нужен отдельный `report`.

## Первый запуск

```bash
npm install --global @rizias/qa-run-triage
qa-run-triage init
```

Настройки — профиль `~/.qa-run-triage/profiles/<имя>/`, один контур со всеми его серверами; файл `profile.json` (серверы, группы джоб, пределы) и рядом `credentials.json` (секреты серверов). Режим задаёт `servers.<имя>.auth`: `none` не требует секретов и не отправляет `Authorization`, `basic` (по умолчанию) требует `proxyUser` и `proxyPass`, `token` требует `user` и `token`. Оба режима с секретами отправляют HTTP Basic с соответствующей парой. В `none` запись сервера в корректном JSON файла секретов и переменные секретов игнорируются; в остальных режимах поля другого режима дают ошибку с именем сервера и поля. По умолчанию действует профиль `default`; другой контур — другой профиль, выбирается флагом `--profile <имя>` у любой команды, переменной `QA_RUN_TRIAGE_PROFILE` или командой `config use <имя>`, которая делает профиль текущим на постоянной основе. `qa-run-triage config init [--profile <имя>]` создаёт профиль с умолчаниями, включая `auth: "basic"` и `report.timeZone` с поясом машины; обязательные для выбранного режима поля вписать руками:

| Поле | Переменная | Что означает |
|---|---|---|
| `servers.<имя>.kind` | `QA_RUN_TRIAGE_SERVER_<ИМЯ>_KIND` | вид сервера, пока только `jenkins` |
| `servers.<имя>.auth` | `QA_RUN_TRIAGE_SERVER_<ИМЯ>_AUTH` | `none`, `basic` (по умолчанию) или `token` |
| `servers.<имя>.baseUrl` | `QA_RUN_TRIAGE_SERVER_<ИМЯ>_BASE_URL` | адрес сервера CI, при необходимости через прокси |
| `servers.<имя>.reportArtifact` | `QA_RUN_TRIAGE_SERVER_<ИМЯ>_REPORT_ARTIFACT` | имя артефакта с отчётом Allure, по умолчанию `allure-report.zip` |
| `servers.<имя>.workspaceNodeMax` | `QA_RUN_TRIAGE_SERVER_<ИМЯ>_WORKSPACE_NODE_MAX` | для kind `jenkins`: до какого номера узла ищется рабочий каталог, по умолчанию 40 |
| `credentials.json`: `<имя>.proxyUser` / `<имя>.proxyPass` | `QA_RUN_TRIAGE_SERVER_<ИМЯ>_PROXY_USER` / `_PROXY_PASS` | пользователь и пароль HTTP Basic для `basic`; прокси необязателен, значения скрыты |
| `credentials.json`: `<имя>.user` / `<имя>.token` | `QA_RUN_TRIAGE_SERVER_<ИМЯ>_USER` / `_TOKEN` | пользователь и API-токен Jenkins для `token`, значения скрыты |
| `report.timeZone` | `QA_RUN_TRIAGE_REPORT_TIME_ZONE` | часовой пояс IANA, по умолчанию пояс машины; неверный пояс даёт ошибку с именем поля |
| `defaultServer` | только в файле | сервер для джоб без совпавшей записи в `jobs`; обязателен, когда серверов больше одного |
| `repos` | только в файле | список абсолютных путей локальных клонов git с кодом автотестов |
| `environment` | только в файле | из каких параметров билда брать `env` и `city`, одно на весь профиль |
| `jobs` | только в файле | маршрутизация на сервер: ключ — джоба или папка джоб, сравнение без учёта регистра; у группы обязательно `server` — имя сервера из `servers`; ключ `*` — ошибка |
| `allowedJobs` | только в файле | граница доступа: джоба вне списка получает отказ; пустой список разрешает все |
| `limits` | только в файле, у каждого предела своя переменная | числовые пределы, таблица в docs/settings.md пакета |
| каталог данных | `QA_RUN_TRIAGE_CACHE_DIR` | по умолчанию `cache/` внутри профиля, в файле поля нет |

Если учётных данных нет — не гадать, а спросить пользователя и назвать, где их взять: `baseUrl` — адрес Jenkins из браузера до первого `/job/`; режим `auth`, логин и пароль прокси — у администратора CI; API-токен Jenkins пользователь создаёт сам (имя справа вверху → Configure → API Token → Add new token, показывается один раз). Проверка: `runs <джоба>` отвечает списком, 401 — неверные данные.

После первых `fetch` и `summary` посмотреть на поле `parameters` в ответе `summary` — оно
печатается целиком, включая значения. Найти среди параметров билда тот, что называет стенд
(и город, если он есть отдельным параметром), и вписать его имя в `environment.env` /
`environment.city` профиля — так `env` и `city` будут заполняться в журнале автоматически.
Узнал такое соответствие — предложить владельцу дописать его в файл заметок (`notesFile`),
своим решением не записывать.

Имя сервера в переменной — заглавными буквами, всё кроме латинских букв и цифр заменено на
`_`; переменные читаются только для серверов, объявленных в `servers`. Два имени с одним
префиксом (`foo-bar` и `foo_bar`) — ошибка. Пустые `--profile`, `QA_RUN_TRIAGE_PROFILE` и
`QA_RUN_TRIAGE_CACHE_DIR` — ошибка с именем флага или переменной. `config init` не сочетается
с `--config`. Переменная важнее файла. Что прочиталось и откуда, показывает
`qa-run-triage config --json`: у каждого поля значение и источник `env`, `file` или `default`,
у `jobs`, `environment` и `report.timeZone` тоже; у серверов показан `auth`, а секреты —
только как «задан» или «не задан» для полей режима. Для `none` признаков секретов нет; пустой секрет из
переменной показан как заданный с источником `env`. Если команда падает, каждое звено причины
печатается строкой `Причина: `.

## Обновление

Если qa-run-triage при запуске сообщил о новой версии — выполни `qa-run-triage update` и
продолжай. Копии скилла обновятся сами при следующем запуске. До первой публикации `update`
завершается кодом 1 с ошибкой E404 — это норма.
